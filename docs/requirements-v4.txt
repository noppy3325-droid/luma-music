LUMA Music 総合修正指示書 v4.0
サブタイトル：Liquid Glassの本格実装・Apple Music水準のUI再構築・ライブラリ高速化・LUMA Enhance音質処理統合

対象: 既存の Android アプリ jp.noppy.lumamusic
開発技術: Kotlin / Jetpack Compose / AndroidX Media3
主な検証端末: Xiaomi 14T
目的: 既存UIを全面改修し、Backdropによる背景サンプリング／屈折表現を実装、フォルダー読み込みを高速化するとともに、LUMA Enhance／Directの音質処理系を安全に追加する。
これは既存プロジェクトの「修正」指示書である。新規アプリを作らず、既存のコード・データ・機能を維持したうえで改修すること。v2のUI修正・スキャン高速化とv3のLiquid Glass実装・回帰条件をすべて引き継ぎ、v4として音質向上機能を追加した統合版である。
添付のスクリーンショット2枚（ライブラリ画面／Now Playing画面）を、現行版の問題点を示す資料として参照すること。可能なら実機で現行アプリも確認すること。

0. 今回の要求と優先順位
現在の初版について、前回までに特定した次の3点が重大な問題になっている。これに加えて今回、本当に音声を加工するLUMA Enhanceと、補正を避けるLUMA Directの実装を要求する。
1. UIが非常にチープで、期待しているApple Music / iOS 26系の洗練されたデザインから遠い。 透明感や情報の階層がなく、巨大な角丸・不揃いな余白・主張しすぎるアクセント色・場当たり的なアイコンで構成されている。
2. 指定フォルダーからの楽曲読み込みが遅すぎる。 スキャン中はライブラリの使用を妨げており、曲を発見してから表示するまでの待ち時間が長い。
3. Liquid Glassが素材として成立していない。 現状は白い半透明の角丸容器に見え、背景の実サンプリング、光学的な輪郭、接触時の動き、レイヤーの一体性が不足している。
P0（最優先）
- Kyant0/AndroidLiquidGlass（Backdrop）の導入可否を実際に検証し、背景サンプリング型ガラス部品を共通化する。 ダミーの半透明surfaceへの置き換えだけでは完了としない。
- ファイル探索・メタデータ抽出・ジャケット処理のボトルネックを計測し、段階読み込み／キャッシュで高速化する。
- ライブラリ画面とNow Playing画面を、Apple Musicの設計原則に沿ってレイアウトごと作り直す。
- アプリを使用中、曲を読み込んでいる最中でも再生とスクロールが妨げられないようにする。
P1
- LUMA Enhanceを実際のPCM処理として実装する。10バンドEQ、適切なヘッドルーム、曲ごとの音量均一化、控えめな自動補正、ステレオ幅調整と安全なバイパスを提供する。UIだけの実装は禁止。
- LUMA DirectとEnhanceを排他的に切り替え、USB-C EarPodsでの再生を維持する。Directの「未加工」と「ビットパーフェクト実証済み」を明確に区別する。
- ミニプレイヤー、タブバー、検索、アルバム詳細、設定画面に共通デザインシステムを適用する。
- 楽曲タグ・アルバムアート・フォルダー指定・進捗表示・再スキャンの品質を改善する。
P2
- 音声補完（DSEE風）の研究プロトタイプは実装可否を検証する。ただし、実際に学習・推論したモデルがない限り「AI補完」とは表示しない。主要機能の完成より優先しない。
- ガラス部品間の融合・分離やインタラクション、共有要素風トランジション、背景色の変化などを丁寧に磨き込む。
- 実機のパフォーマンスを測定し、スクロールのジャンクや再生中の余計なCPU負荷を抑える。
絶対にしないこと: 効果のない音質向上スイッチの追加、デコード後のPCMを書き換えずに「高音質化済み」と宣言すること、ヘッドルーム不足による歪み、Directモードでの隠れたEQ適用、原因を調べずにスキャン処理の待機時間を短く見せるだけ、色だけを替える、画面に半透明ボックスを追加して「Liquid Glass対応済み」とする、ライブラリ導入だけで使わない、動作未確認で「完全再現」と称する、再生・フォルダー指定などの既存機能を壊す。

重要な到達点: Apple内部のLiquid Glassレンダリングそのものと完全同一にはできない。一方で、見た目・手触り・画面構成は高い水準まで近づけられる。「完全同一」を名乗ることより、実機で背景の屈折と動作が確認でき、違和感のない完成度であることを重視する。

素材について: Apple Musicの画面構成は参考にするが、Appleロゴ・アイコン・SF Pro・純正画像などを無断同梱しない。LUMAという独自アプリ名・識別子を保持する。
1. 現行スクリーンショットの具体的な問題点
1-1. ライブラリ画面
- LUMA / YOUR MUSIC のピンクの英字サブ見出しが装飾的すぎ、ライブラリ画面の主役を奪っている。原則削除。ブランド表現は控えめに。
- ライブラリ の見出しは大きいが、上部の余白と見出し・検索・フィルター間の距離が不均一。大見出しを軸に統一した垂直リズムへ。
- 検索ボックスの黒っぽい太い枠線・高さ・角丸が強すぎる。iOS系の薄い、背景になじむ検索フィールドに変更。
- カテゴリーチップが大きく、枠線や選択状態が古いWeb UIのように見える。小さく柔らかいピル型・控えめな選択状態にする。
- 画面中央に巨大な空き領域があり、読み込み中なのに「音楽がありません」という空状態が表示されている。スキャン中・ゼロ件・エラー・権限喪失を区別すること。
- 追加ボタン・フォルダー選択ボタンのピンクが目立ちすぎる。機能上必要な強調だけに絞る。
- 下部の太いピンクの読み込みゲージと巨大な白いナビゲーションパネルが分離して浮いて見える。スキャン表示は画面を圧迫しない小さなステータス表示へ。
- タブが「ライブラリ／設定」の2つだけで、検索が画面上部に巨大なパーツとして居座っている。情報構造を再考する。
1-2. Now Playing画面
- 青い背景グラデーションが広範囲で単調。アートワークの色を使った低周波・低コントラストの背景へ。ジャケットの鮮やかさを主役にする。
- 上部の NOW PLAYING 英字、ピンク、斜体、`不明なアルバム` が不自然に目立つ。再生画面のヘッダーは最小限。アルバム不明なら無理に表示しない。
- ジャケットの大きさ自体は魅力だが、画面の上下が間延びし、ジャケット・曲名・シーク・操作部のリズムがない。小画面でもすべての重要操作に届く可変レイアウトへ。
- 楽曲名 ライラ とアーティスト esoragoto の書体・太さ・斜体の組み合わせがちぐはぐ。日本語とラテン文字を統一感のあるサンセリフ系にする。アーティストの斜体はやめる。
- シークバー左の縦線、太い白いトラック、端の赤い点が一体化していない。薄く一体感のあるスライダーにする。
- 再生ボタンの巨大な蛍光ピンク円が画面から浮いてしまっている。標準的な音楽プレイヤーとしてのシンプルな再生・停止コントロールにする。
- 前後送り・シャッフル・リピートのアイコンサイズ、色、配置に統一感がない。
- 最下部の白い巨大な角丸容器に3つの意味不明なアイコンが並んでいる。歌詞・出力先・キューなど役割が直感的にわかる操作にして、透明感のある薄いコントロール領域へ統合する。
- ステータスバーが明るい背景で黒いままなど、背景とのコントラスト・System Barsの調整が不足している可能性がある。
補足: これはスクリーンショットに基づくUIレビュー。コード上の原因やスキャンの遅延箇所は未確認なので、推測を断定せず計測で確定すること。
2. デザイン再構築の基本原則
2-1. Apple Musicらしさを「ルール」で再現する
iOS 26のApple MusicとAppleのHuman Interface Guidelinesを視覚的な参考にする。ただしAppleのロゴ、独自アセット、商標表現、無断コピーしたデザイン素材は使わず、LUMA独自の音楽アプリとして成立させる。

重視するのは次の順番。
1. コンテンツを主役にする: ジャケット・楽曲名・アルバムが目立ち、装飾は補助。
2. 階層を明確にする: 大見出し／セクション／本文／補助情報／操作を文字サイズと余白で区別。
3. ガラスを使いすぎない: Liquid Glass風効果はタブバー・ミニプレイヤー・シート・操作UIなど機能レイヤー中心。本文・カード・背景を全部ガラス化しない。
4. 形を統一する: 角丸、内側余白、ボタンサイズ、アイコンの線幅を共通トークンにする。
5. 動きの連続性: 開く・閉じる・曲が替わる・スクロールする際に位置関係が自然につながる。
6. 文字に品格を与える: 意味のない英字装飾、斜体、字間の広さ、派手なピンクを廃止する。
2-2. デザイントークンの目安
これらは初期値。実際の端末スクリーンショットで調整すること。
要素	初期指針
外側の左右余白	20〜24dp
大見出し	34〜38sp / Bold、必要なら端末幅で可変
セクション見出し	21〜24sp / Semibold
曲名	一覧 15〜17sp、再生画面 24〜30sp
補助情報	12〜15sp、低コントラストだが読める色
基本余白	4 / 8 / 12 / 16 / 24 / 32dpのスケール
検索フィールド	高さ 46〜52dp、目立つアウトラインなし
フィルターチップ	高さ 32〜38dp、1px相当の強い枠線は極力避ける

色設計：
- ライトテーマ: ニュートラルに近い明るい背景、濃い文字、控えめなセパレーター。
- ダークテーマ: 深いチャコール／ほぼ黒、読みやすい白文字。
- アクセント: LUMAのピンク系を継承してよいが、リンク、選択、アクティブ状態に限定し、主再生ボタンや大面積パネルを塗りつぶさない。
- プレイヤー背景: ジャケットの代表色から生成した彩度を抑えた多層グラデーション。コントラストを確保。
- 文字: Androidで正当に利用可能なフォント（日本語対応のシステムサンセリフ等）を用い、SF Proを無断同梱しない。
- アイコン: Material Symbols等をベースにスタイル・線幅・光学サイズを全画面で揃える。意味不明な独自記号を作らない。
コンポーネントライブラリを LumaTheme / LumaColors / LumaTypography / LumaSpacing / LumaShapes として共通化すること。画面ごとのマジックナンバーを減らす。
2-3. 今回の核心：BackdropによるLiquid Glass描画エンジンの実装
採用ライブラリ
第一候補: Kyant0/AndroidLiquidGlass（ライブラリ名：Backdrop、Apache-2.0）。
- 公式ドキュメント: https://kyant.gitbook.io/backdrop
- API概要: https://kyant.gitbook.io/backdrop/api/backdrops
- 公式サンプル: https://github.com/Kyant0/AndroidLiquidGlass/tree/kmp/app/src/commonMain/kotlin/com/kyant/backdrop/catalog/components
- 参照コンポーネント: LiquidButton.kt / LiquidToggle.kt / LiquidSlider.kt / LiquidBottomTabs.kt
- Gradle座標: io.github.kyant0:backdrop:<version>（Maven Central経由。利用可能な安定バージョンを実際に調べて固定すること）
2026-11-09時点で確認したリポジトリのGradle設定は 2.0.1 を示しているが、これを無条件に最新版・配布済みと決めつけず、Maven Central上の公開状況と現在のプロジェクトのKotlin/Compose/AGPとの互換性を確認すること。`+` や動的バージョンを本番設定に使用しない。

特に重要: Backdropは高水準のUIコンポーネントを完成品として配布するライブラリではない。READMEに記載された LiquidBottomTabs などは実装参考のサンプル。サンプル名をそのまま import できると仮定せず、公開APIの Backdrop / rememberLayerBackdrop / Modifier.layerBackdrop / Modifier.drawBackdrop など（使用版で確認）を用いて LUMA用の独自コンポーネントを実装すること。

例示（API概念・導入候補。貼るだけでビルド可能と断言しない）：
// app/build.gradle.kts：まずリリースと互換性を確認する
// dependencies {
//     implementation("io.github.kyant0:backdrop:<検証済み固定バージョン>")
// }
依存導入に際しては、README、公式ドキュメント、使用バージョンのソース、実際のGradle解決結果を照合すること。サンプルはライブラリの公開APIと分けて扱う。
物理的な素材感として必要な表現
1. Live backdrop sampling: パネルの背後にある画面内容を実際に取り込む。固定背景色だけの偽ブラーは禁止。
2. Blur: 背景の情報量を落とす。文字やアイコン自身はぼかさない。背景と前景の描画レイヤーを分ける。
3. Refraction / lens: ガラスの縁や表面で背景が局所的に屈折する。過剰な波打ち・歪みは禁止。
4. Vibrancy / luminance: 背景に応じて明暗と彩度を調節し、文字・アイコンの視認性を確保する。
5. Edge highlight & shadow: ごく細い光の縁・内側の明暗・低い影で厚みを示す。厚い白枠は禁止。
6. Motion: 押下・選択移動で軽いスケール/ハイライト/流動的な遷移を与える。クリック応答は即時。
7. Containment: 高負荷なガラスは操作レイヤーに限定し、各曲のリスト行に毎回shaderを付けない。
実装上の重要ポイント: Androidの単純な Modifier.blur() は、それを付けた要素自身をぼかす動作であり、背後の独立した兄弟レイヤーを自動で屈折させるわけではない。`Backdrop` の取得対象・描画順・座標系を正しく組み立てる。画像のジャケットまで常に曇らせないこと。
推奨シーングラフ
LumaScreenRoot / Edge-to-edge
├─ Background layer
│   ├─ Base color / artwork palette / subtle gradients
│   └─ Scrollable content (when the glass floats above it)
├─ Backdrop recording layer  ← ライブラリの使用版に合った記録方法
└─ Foreground interactive layer
    ├─ LumaGlassMiniPlayer
    ├─ LumaGlassTabBar
    ├─ LumaGlassFloatingAction
    └─ LumaGlassSheet / popup
        └─ 前景のテキスト・アイコンは屈折せず、くっきり表示
次のミスを防ぐこと。
- ガラス自身を背後ソースに含め、再帰的にサンプリングすること。
- 画面全体のスクリーンショットを毎フレームCPUで取り込むこと。
- 異なる座標系のBackdropをそのまま共有して位置ずれを起こすこと。
- ダイアログやシートに別Windowを使う際、背後が取得できると決めつけること。取れない場合は独立したBackdropか近似表現へ切り替える。
- Compose状態が更新されるたびに巨大なビットマップやShaderを再生成すること。
designsystem/glass/ を作成
既存パッケージ構造に合わせ、次の責務を設ける（名前は構造の例）。
designsystem/
  theme/                 LumaTheme / colors / type / spacing / shape
  glass/
    LumaGlassHost.kt      背景記録・座標変換・ホスト状態
    LumaGlassSurface.kt   視認性と材質の共通設定
    LumaGlassButton.kt    クリック・押下・48dpタップ領域
    LumaGlassTabBar.kt    選択表示・選択項目の遷移
    LumaGlassMiniPlayer.kt
    LumaGlassSlider.kt    シーク用。正しい操作性を優先
    LumaGlassSheet.kt     キュー/メニューなどのオーバーレイ
    GlassQuality.kt       High / Balanced / Reduced / Off
既存の再生ロジックと描画を疎結合にする。 たとえば LumaGlassMiniPlayer は PlaybackUiState を受け、操作イベントをコールバックで送る。PlaybackServiceをガラスコンポーネントから直接参照しない。
最初に小さな技術検証（必須）
ライブラリをアプリ全体へ広げる前に、既存プロジェクト内のデバッグ用画面または隔離されたデモを作る。
- 背後で色の異なるジャケットと文字付きのリストがスクロールする。
- 前面に小さなピルとタブバーを浮かせる。
- 背景が動くとガラス内部のぼけた像も変化することを実機で検証。
- エッジ部分で局所的な屈折とハイライトを確認。
- 明るい背景・暗い背景・高彩度のジャケット・グレー背景の各条件で文字を読む。
- タッチ、連続スクロール、画面回転でちらつき・黒い矩形・位置ずれがないことを確認。
この検証を通過するまで、UI全画面をいきなり書き換えない。 ただし検証だけで停止せず、成功した方式で本番画面を順に改修する。
代替候補とフォールバック
Backdropが既存Kotlin/Composeの制約で導入できない、描画不具合が出る、実機性能が不十分な場合だけ、PrismalAGSL（MIT）を比較検証する。PrismalAGSLにはCompose向けガラス部品とAPI別フォールバックがあるが、Kotlinバージョン・JitPack・リリースアーティファクトの確認が必要。2つの効果ライブラリを無計画に重ねて二重ブラーにしない。原則1エンジンに統一する。
- API 33+ ではAGSLなどによる高度な効果が利用可能。公式資料：https://developer.android.com/develop/ui/views/graphics/agsl
- 下位APIでは使用するライブラリの実際の対応範囲を確認し、必要に応じて簡素な半透明/ぼかしへ切り替える。
- minSdk を都合よく上げて既存サポート端末を切り捨てない。どうしても変更が必要な場合は理由と影響を報告。
- フォールバックを使っても、UI配置と操作性は同じ品質で提供する。
2-4. 実際の画面に適用するガラスの階層ルール
対象	ガラスの使い方	やらないこと
ボトムナビ	背景を透かし、選択箇所を穏やかに強調する低いピル	横幅いっぱいの白い大箱、常時強いぼけ
ミニプレイヤー	背景が動く軽いブラー、曲名を読むための適切な明度	ジャケット自体をぼかす、タップしづらくする
Now Playing下部操作	必要な小型ボタン/シートだけガラス化	巨大な半透明パネルでアートワークを圧迫
再生・一時停止	高コントラストの明快な主操作。ガラスは任意	大きな蛍光ピンクの塗りつぶし
検索欄	静かな低コントラストの入力領域。実効性優先	重い屈折と光沢で文字入力を邪魔する
歌詞オーバーレイ	歌詞の可読性最優先、操作部だけガラス	全歌詞をガラスの内側に入れる
スタンバイ画面	右の操作パネルに限定的に適用	画面全体をガラス一枚にする


判断基準: ガラスがなくても画面情報設計が成立し、ガラスを有効化すると素材感だけが自然に向上すること。見た目を誤魔化すフィルターとして使わない。
2-5. Liquid Glassの性能・アクセシビリティ
- GlassQuality = High / Balanced / Reduced / Off を用意。既定は実機計測に応じて決める。UIで手動変更でき、再起動後も保持する。
- Off はフラットだが同一レイアウト、`Reduced` は背景ブラー/屈折の負荷を落とす。端末が効果を扱えない場合の自動フォールバックを用意する。
- remember / derivedStateOf 等でシェーダー・ブラシ・解析済みカラー・shapeを使い回し、再Composeごとに重いオブジェクトを生成しない。
- スクロール中の全コンテンツを高解像度で多重描画せず、サンプリング範囲・解像度を最適化。
- 降下・上昇アニメーション中や画像切り替え時に描画更新をまとめる。無音時に無意味な常時アニメーションを走らせない。
- ライト/ダーク、高彩度・低彩度・真っ白/真っ黒ジャケットで読みやすさを維持。WCAGのコントラストを可能な範囲で検証する。
- Androidのアニメーション縮小やユーザー設定に従う。TalkBackの読み順・操作ラベル・最小タッチ領域を保持。
- Xiaomi 14Tの実機でスクロールと再生中を測る。60fpsは最低目標、端末の表示モードで高リフレッシュレートが利用できる場合はそれも考慮。
計測指標: 修正前後でJankStats / Macrobenchmark / Perfetto等を使い、フレーム時間の中央値・p95・遅延フレーム割合、CPU/GPU負荷、メモリ、電池消費の変化を可能な範囲で記録。ビルドはDebugではなくRelease相当を主体とし、計測不能なら未測定と報告する。
3. ライブラリ画面の改修仕様
3-1. 画面構成（上から）
1. ヘッダー: ライブラリ。右上にはフォルダー追加の小さなアクション。不要な英字サブタイトルは消す。
2. 検索: 薄い塗りの検索欄。常時表示する場合も高さを抑える。タブに検索を分離する案も含めて、重複を避ける。
3. ナビゲーション: 最近追加 / アルバム / アーティスト / 楽曲 / フォルダー / プレイリスト を見通せるチップまたはカテゴリ一覧。横スクロールがある場合は末尾の見切れでそれが自然にわかるようにする。
4. コンテンツ: アルバムグリッド／楽曲リスト／カテゴリ別一覧。曲が発見された時点から順次表示。
5. ミニプレイヤー: 再生曲が存在するときだけ表示。タップでNow Playingへ。
6. フローティングタブバー: ライブラリ・検索・プレイリストなど、必要な主要ナビゲーションを設ける。設定は右上などセカンダリーに置く案を優先。
3-2. 状態設計（重要）
状態を明確に分けること。
- NoFolderSelected: フォルダー未選択。初回案内とフォルダー指定CTA。
- Scanning: スキャン中。現在発見した曲をすぐにリスト表示し、小さな進捗テキスト 音楽を読み込み中 · 46曲見つかりました を提示。大きな空状態を同時表示しない。
- Ready: 曲一覧表示。スキャンは裏で続いていてもよい。
- Empty: スキャン完了したのに対象音源がゼロ。はじめて本当の空状態を出す。
- PermissionLost: フォルダーのアクセス権喪失。再選択を案内。
- PartialFailure: 一部曲だけ解析失敗。成功曲は利用可能にし、詳細を開けるようにする。
初回スキャン中は全画面モーダルや操作不可のローディングを置かない。再スキャン時は前回のライブラリを維持する。
3-3. ミニプレイヤーと下部ナビゲーション
- 再生曲のジャケット、小さめの曲名、再生/一時停止、必要なら次へ。
- 余白と角丸は画面に合わせ、巨大な霧状の白パネルは使わない。
- 背景に連続したコンテンツがあるときのみ、適切なブラーや半透明表現を使う。
- ナビゲーションバーの下端はジェスチャーバーと重ならない。
- スクロール時の縮小やタブバーとの一体化は、操作可能性を保てるなら導入する。
3-4. スクロールとガラスの実動作に関する受入条件
- リストの後ろに浮かぶタブバー/ミニプレイヤーで、背後にジャケットが近づくとガラス内の色味が変化する。
- ミニプレイヤーとタブバーを二重に囲う巨大な白いパネルは禁止。別部品でも視覚的には一続きに感じられる位置・サイズ・影にする。
- コンテンツ領域の最下部には適切な余白を付与し、最後の行がタブバーに隠れない。
- 読み込み中の進捗は小さな情報表示か静かなインジケーターとし、楽曲が見つかった瞬間から閲覧/再生できる。
- スクロールとライブラリ更新で同じ項目が何度も揺れたりリスト全体が再構築されたりしない。
- ユーザーがスクリーンショットを見ただけで、現在の「大きな枠線・ピンクの装飾・巨大な白い下部バー」から明らかに別デザインと分かること。
4. Now Playing画面の全面再設計
4-1. 情報配置
画面上部から：
1. 小さな閉じるシェブロン。中央のヘッダーは必要ならアルバム名などごく控えめに。不明なアルバム名を強調しない。
2. 大きなジャケット。画面高さに応じて可変（小さい端末でシーク・操作が隠れないこと）。
3. 曲名を第一階層、アーティスト名を第二階層で表示。長い曲名は適切に省略・スクロールを制御。
4. 細いシークバー（通常2〜4dp程度、操作時は拡大してもよい）。現在時刻と残り時刻を左右に。
5. 前へ・再生/一時停止・次への主要3コントロールを同じデザイン言語で中央揃え。
6. シャッフル・リピートは控えめな補助操作。状態変化はアクセントでわかるように。
7. 歌詞・音声出力・キュー・スタンバイモードなどの補助操作を下部の軽量なバーへ。必要なら二次操作をメニューに移す。
4-2. 強制修正事項
- 巨大な蛍光ピンクの「再生丸ボタン」を撤去し、背景色とのコントラストで成立するシンプルなコントロールに変更。
- 不要なピンクの NOW PLAYING、斜体のアーティスト表記、意味不明な上部アイコンを撤去・再設計。
- シークバーの縦ピンク棒・端のピンク点・太い白い矩形をやめ、滑らかな統一スライダーに変更。
- 下部の大きな白い長方形を軽量化。機能の意味はラベル、ツールチップ、アクセシビリティテキストでも伝える。
- 背景はアートワーク主導。色が強すぎる・白文字が読めない・ステータスバーだけ黒い、という状態をなくす。
- アートワークは中央に美しく配置。正方形・元画像比率・角丸・影を一定ルールで処理。
- 小画面・大画面・システムフォント拡大・ジェスチャーナビゲーションで崩れない。
4-3. 動きとLiquid Glass
- 曲変更時: アートワークが自然に入れ替わり、背景が300〜600ms程度で穏やかに変化。
- ミニプレイヤー → 全画面: 共有要素のような位置・サイズの連続性。実装コストが高ければ、質の高いフェード/スライドで代替。
- シートとフローティングコントロール: 薄い背面ぼかし・境界ハイライト・自然な押下フィードバック。ただし毎フレームの高解像度背景キャプチャは避ける。
- reduced motion / 省電力モードではアニメーションと高負荷効果を軽減。
技術方針: 単に`alpha=0.4f`や`Modifier.blur()`を重ねても「背後が屈折して見えるガラス」にはならない。どのレイヤーの何をぼかすか、再描画頻度・パフォーマンス・視認性まで設計し、Androidで実現可能な材質感として完成させること。
4-4. Now PlayingでのLiquid Glass配置と画面縦寸法への対応
- ジャケットは主役。高解像度・彩度を残してそのまま表示。ガラス越しにぼかしてはいけない。
- 背景はジャケットの色から計算してキャッシュした低周波グラデーションとし、再生位置の更新で毎秒パレット計算しない。
- シークバーは操作性が重要。Backdropを使った見た目を採用しても、タップ/ドラッグの連続性と位置精度を優先する。
- 主再生ボタンは背景に応じた白/黒のシンプルなアイコンを使用。派手な色面を避ける。
- 歌詞・キュー・出力切替・スタンバイは下段の小さなガラス操作ボタン/軽量バーで統一。意味が分からない装飾アイコンを禁止。
- ジャケットの縦寸法は固定で大きくしすぎない。WindowInsets・ステータスバー・ナビゲーション・画面縦横比に合わせて上限を算出し、小画面で下部の主要操作がはみ出さないこと。
- 画面遷移は共有要素ライクな動きを目指すが、アイコンが置き去りになったりジャケットが一瞬消えたりするくらいなら品質の高いシンプルな遷移を選ぶ。
簡単な手動検証: 青・ピンク・黒・白のジャケットを順に再生し、すべてで文字と主要操作が読め、ガラスの色と屈折が背景に追従することを確認する。
5. 楽曲読み込み高速化：最優先の実装修正
5-1. 原因を先に計測する
現在のスキャンを以下の時間に分解し、端末で実測・ログ出力する。
1. SAFツリー走査（ディレクトリー列挙）
2. 対象ファイル判定
3. メタデータ抽出（曲名・アーティスト・アルバム・再生時間）
4. 埋め込みアートワーク抽出／デコード／縮小
5. DBの挿入・更新
6. 一覧初表示までの時間
7. スクロール中の描画・CPU・メモリ
LogcatやTraceを利用し、平均・p95・最大を把握する。まず現行版でベースラインを採ること。推測だけで原因を決めつけない。
5-2. 3段階・非同期パイプライン
Stage A: ファイル発見（高速、最優先）
- ユーザーが選択したフォルダーのみ、子フォルダーを含めて探索する。
- SAFの場合は`DocumentsContract.buildChildDocumentsUriUsingTree()`等を用いたディレクトリー単位の列挙を検討し、必要な列（documentId、displayName、MIME、size、lastModified）のみ取得。
- DocumentFile.listFiles()を使った実装がボトルネックなら、プロバイダーの仕様に合わせてクエリ回数を削減。
- 可能な場合はMediaStoreの索引活用も比較。ただしユーザーが許可したフォルダーに限定すること。パスの不安定な変換、無断の広範なライブラリ収集は禁止。
- 曲を発見するたび、ファイル名・URIから仮の楽曲項目を生成し、全件スキャン完了を待たずにリストとDBへ逐次反映する。
- 重複を避け、取得したURI・documentId・size・lastModifiedなどを保持する。
Stage B: メタデータ取得（バックグラウンド）
- UIとは別の`Dispatchers.IO`ワーカーで実行し、取得が終わった曲からUIを更新。
- MediaMetadataRetrieverまたは`Media3 Inspector MetadataRetriever`を比較し、対応形式とコストから選択。使用後のリソースは必ずclose/release。
- 並列度は2〜4件程度から計測で調整。全曲一斉にスレッドを起こさない。
- 再生中／画面に表示中／ユーザーが選択した曲を優先し、残りを後で処理。
- 曲名やアルバム情報が欠ける場合、ファイル名などへのフォールバックを適切に行い、未知の情報を捏造しない。
Stage C: ジャケット画像・歌詞・重い解析（低優先）
- 全曲の高解像度アートワークを初回一括展開しない。
- 表示が必要な曲から非同期抽出し、一覧用にはサムネイルをキャッシュ。
- アルバムアートはメモリキャッシュ＋ディスクキャッシュ。再スキャンで同じ画像を再デコードしない。
- 歌詞解析、背景の代表色算出、高音質情報抽出などは初回一覧表示のクリティカルパスから分離する。
- 画面で見えない曲の画像処理がCPU・メモリを占有しないようにする。
期待する処理順序:
フォルダー選択
   └─ 子項目をバッチ取得
        ├─ 曲の仮レコードをRoomへ逐次保存 → Flow → 楽曲一覧に即表示
        ├─ メタデータを限定並列で補完 → 行だけ更新
        └─ 表示対象のアートワークを遅延取得 → キャッシュして描画

通常起動
   └─ Roomから既存ライブラリを即表示
        └─ 必要時だけフォルダーの差分チェック
5-3. 増分スキャンとキャッシュ
- フォルダーURI・楽曲URI/documentId等で一意識別し、size・更新日時などで差分を検出。更新日時等が欠落するプロバイダーでは保守的に再確認。
- 変更のないファイルはタグ・ジャケットを再解析しない。
- 通常起動時はDBに保存済みの曲を即表示。同期・差分確認が必要でもバックグラウンド実行。
- フォルダー再指定や強制再スキャン時も古い一覧を消さず、新しい情報を安全に反映。
- スキャン結果の削除は「今回見つからなかった」だけで即断しない。アクセス権喪失・一時的I/Oエラー・プロバイダー不調を区別する。
- 途中でアプリを閉じても部分成果を保持。再開・キャンセル・再試行に対応。
- 同一アーティスト/アルバムの集計はDBクエリや事前集計を使用し、描画のたびに全曲を走査しない。
5-4. UIと再生の独立性
- LazyColumn / LazyVerticalGrid に安定した key と適切な contentType を指定。
- 状態変更時にリスト全体を組み直さず、変更されたアイテムが中心に再Composeされるようにする。
- 再生位置の更新でライブラリ全体が毎秒再描画されるような状態設計を禁止。
- Room→Flow/StateFlowを通じた細粒度の更新。大量の行を毎回丸ごと作り替えない。
- タグ解析やジャケット復号はUIスレッド上で行わない。
- 検索は入力に軽いdebounceを使い、必要に応じてRoom上で実行。大きな全件リストを毎キー入力で重く処理しない。
- Media3のバックグラウンド再生はスキャンとは独立し、楽曲発見中・回転中・画面遷移中にも停止しないこと。
5-5. 可視化とパフォーマンス目標
測定条件: Xiaomi 14T実機・同じ楽曲フォルダー・Release相当ビルド。初回・2回目以降・強制再スキャンを分ける。ファイル数、フォルダー深度、FLAC/MP3比率を記録。

目標値（現状値ではない。端末・SAFプロバイダー・ファイル特性によって調整してよい）:
- 2回目以降の起動で保存済みライブラリの主要部分が1秒前後で表示されることを目標。
- 初回は全タグ解析完了を待たずに、最初に見つかった曲を数秒以内に一覧表示することを目標。
- 100〜200曲規模なら数秒〜十数秒以内に基本メタデータを利用可能とする目標を設け、実測で妥当性を確認。
- 1000曲以上でもスキャン進捗が更新され続け、通常のリスト操作と再生が妨げられないこと。
- 通常スクロールでは60fps相当の滑らかさを目指し、Perfetto / Macrobenchmark / JankStats等で改善前後を比較。
- スキャン中の連続再生に音切れ・明らかなUIフリーズがないこと。
必須レポート: 実測で「フォルダー列挙」「タグ解析」「画像解析」「初回表示」「2回目起動」がそれぞれ何ms/何秒だったかを改修前後で表にする。数値を測っていない場合は未測定と記載。
5-6. 追加の実装詳細：スキャン遅延を再発させない設計
目的は「すべて読み終えるまで0件」から「発見した曲がすぐ使える」への変更。 速度を稼ぐために重複したスレッドを大量作成したり、初回だけキャッシュをハードコードしたりしない。
- ScanCoordinator はフォルダー単位の状態を持ち、同じフォルダーに多重スキャンを発生させない（Mutex 等）。
- SAFプロバイダーはローカルだけとは限らない。個別IPCの多い再帰処理は高コスト。1ディレクトリーのクエリ列挙・必要列限定・Cursorの確実なcloseを優先する。
- DocumentsContract で得たURIを永続権限と紐づける。無断でファイルシステムの実パスへ変換しない。
- ファイル発見は bounded channel / バッチDB upsert。1件ごとの同期Room transactionと大きなUI更新を避ける。
- メタデータ抽出は Semaphore 等による限定並列、キャンセル対応、タイムアウトや破損ファイルの隔離。MediaMetadataRetrieverのハンドルを必ず解放する。
- サムネイルのディスクキャッシュキーは URI + size + lastModified + (必要ならalbumId) のように、内容変更を判別できる形にする。ただしプロバイダーがメタ情報を返さないケースに対処する。
- 初回は一覧表示中の曲を先に解析し、残りは後回し。再生中の曲が最優先。歌詞解析・詳細技術情報・アートワーク色抽出は遅延可能。
- すでに保持するRoomのデータを先に表示。バックグラウンドの再スキャンで古いレコードをいきなり全削除して再登録しない。
- 重複ファイルの扱いは安定した識別子で判断する。同一曲名でも異なるファイルなら勝手に統合しない。
- フォルダーが読めなくなったら PermissionLost、一部失敗は PartialFailure。全部0件へ落とすのは禁止。
- 大量の再Composeの原因になりやすい playbackPosition をライブラリrootに流さず、ミニプレイヤーとシーク部だけ購読する。
5-7. 測定シナリオと具体的な提出物
同一端末・同一フォルダー・同一APKビルド設定で、以下を修正前後に計測する。
シナリオ	計測項目	期待する状態
初回スキャン（例：50 / 200 / 1000曲）	最初の1曲が現れるまで、A/B/Cの完了時間、総時間	全曲メタデータ完了を待たずに部分表示
2回目起動	Room→一覧初表示、追加ファイル差分確認	保存済み一覧を先に即表示
未変更フォルダー再スキャン	再解析曲数、DB更新数、総時間	変更なしを再解析しない
10曲追加・5曲削除	差分検出精度、一覧の更新、再生キュー	既存の曲を消さない・削除反映は安全に
読込中に再生・スクロール	フレームp95、オーディオ中断、メモリ	音切れ・固まりなし
ショートカットでフォルダー再指定	権限・重複・再帰処理	既存プレイリストなど保持


スキャンUIの時間ではなくファイル探索/タグ解析/画像処理の実測時間を示す。ログの抜粋と、遅延原因に対して何を修正したかを最終レポートに記載する。
6. 既存機能の維持と回帰防止
今回の主眼はUI/UX・読み込み速度・音質処理だが、従来の開発方針も保持すること。
- Kotlin + Jetpack Composeのまま（WebViewに移行しない）
- 指定フォルダーだけを読み込むSAF方式と永続URI権限
- MP3 / AAC / FLAC / WAV / OGG / Opus等の端末対応範囲
- 楽曲タグ、ジャケット、アルバム、アーティスト、プレイリスト、歌詞
- バックグラウンド再生、MediaSession、通知、ロック画面、Bluetooth操作
- Xiaomi HyperIsland: 公式の対応条件に従い標準メディア通知/MediaSessionから連携。非対応環境で偽装しない。ガラス描画改修で通知ロジックを触らない
- スタンバイモード: 明示的な操作後に横置きで起動。左ジャケット・右操作部。画面回転で再生を失わない
- Apple EarPods（USB-C）を含むUSB音声出力。通常出力とビットパーフェクトの検証済み状態を区別。ビットパーフェクトの未検証を「対応済み」と偽装しない
- LUMA Enhanceが有効な場合はDirect/ビットパーフェクト扱いにしない。 音声処理が使えない経路では機能の利用可否と理由を示し、勝手に嘘のステータスへ切り替えない
- 既存Roomデータ・プレイリスト・フォルダー権限・設定の互換性。スキーマ変更時は適切なマイグレーション。`fallbackToDestructiveMigration` によるデータ消去を安易に使用しない
- 切断・権限喪失・デコード失敗があっても既存の音楽ファイルを消去しない
今ある機能を削除して見た目だけを完成させないこと。
7. v4で追加する音声機能の目的と適用範囲
7-1. LUMA Enhance と LUMA Direct
音質は「元の音への忠実さ」と「聴き心地の好み」を混同しない。圧縮によって消えた成分は、EQやコンプレッサーだけでは復元できない。「音質向上」はユーザーが好みに調整できる音声処理の総称として扱い、加工が原音の客観的な改善であると断定しない。
モード	信号の扱い	使用可能機能	状態表示
LUMA Enhance	デコード済みPCMにDSPを適用	EQ、音量均一化、自動補正、ステレオ幅、必要ならLimiter	音質補正 ON、有効な処理一覧
LUMA Direct	LUMA自身のDSPを完全にバイパス	元の再生、キュー、シーク、通知等	アプリ内補正 OFF。ビットパーフェクトかどうかは別途検証


- 初期状態はDirect相当の補正OFF、またはユーザーが初回設定で選択。勝手に音色を変えない。
- LUMA EnhanceではPCMサンプルを実際に加工する。UIの視覚効果だけでなく、出力PCMに測定可能な変化があること。
- LUMA Directはアプリ側DSPを使わないことを保証する名称。Androidのミキサー、システムEQ、DACの内部処理まで無加工とは言えない。`Bit-perfect`は実際に検証できた場合のみ別表示。
- モード切替によってMediaSession、再生曲、キュー、シーク位置、サービスが壊れないこと。
- 音量急増を防ぐため、遷移時のゲインランプ／安全な再構成を実施。エンジン再作成が必要なら再生位置の保持と短いフェードを行い、その制約を記録する。
- EQを有効化したまま「ビットパーフェクト」のラベルを付けてはいけない。
7-2. 実装する優先順位
MVP（必須・実際に動かす）
1. Enhance/Directの二択と、適用中の実際の処理状態を表示。
2. 10バンドパラメトリック/グラフィックEQ（実装方式は検証して決定）、プリセット・手動保存・リセット。
3. クリッピングを防ぐヘッドルーム処理、オーバーフロー・NaN保護。
4. 音量均一化（まず既存タグ、次に任意の非同期ラウドネス解析）。
5. 保守的な自動音質最適化（誇張しないアルゴリズム）。
6. ステレオ幅の調整・モノラル互換性。
7. 出力デバイス別の表示・設定保存とUSB-C EarPodsでの安全な再生。
発展機能（主要機能が完成してから）
- 軽いマルチバンド圧縮、必要に応じたTrue-Peak Limiter、低域位相補正の研究。
- DSEE風の圧縮音声補完は実験機能として研究する。ただし、既存モデルを連携しただけ・高音EQだけを掛けただけで「AIによる復元」と表示しない。

8-2. 推奨する実装方式
第一候補：Media3 PCM AudioProcessor連携
- 使用するMedia3バージョンの公式APIを確認し、`BaseAudioProcessor` / AudioProcessor と DefaultAudioSink.Builder.setAudioProcessorChain(...) または検証済みの相当APIを利用する。
- DefaultRenderersFactory / audio sinkの実際の組み立て方は採用Media3版のソースとサンプルを確認する。存在しないビルダーAPIを推測で書かない。
- PCM処理には制限があり、オフロードやパススルー経路には適用できない。Enhanceを利用する際はPCM経路が確保されるよう、該当機能を正しく無効化または切り替える。切替失敗時はユーザーに表示。
- PCM 16bit・float・44.1/48kHz等の対応範囲を明示し、未対応形式は適切に変換または安全にバイパスする。意図しない多段リサンプリングは避ける。
- ストリーム間でsampleRate、channelCount、encodingが変わってもフィルター係数・バッファ・メモリを正しく更新する。
- 再生コールバックに重い分析処理、I/O、DBアクセスを入れない。DSPのリアルタイム処理部分は固定長/再利用バッファを使用し、頻繁なアロケーションを避ける。
- モード切替・DSPパラメーター変更はスレッドセーフな設定スナップショットで更新し、割込み時に不完全な設定を観測させない。
代替候補：Android Equalizer / DynamicsProcessing
- 適切なAudioSession IDに紐づけて使用できる。ただしOEM差、利用可能バンド数、周波数、オンオフ、同時適用可否が異なる。
- Android Equalizer は端末で必ず10バンド使えるとは限らない。`getNumberOfBands()`と`getBandLevelRange()`で実測し、10本固定UIならその値を正直に写像する、または10バンドの自前PCM DSPへ切り替える。
- DynamicsProcessingは実装差・バンド構成・セッション対応を確認。システムの音響エフェクトと自前DSPを二重適用しない。
- APIが機能しない端末で、スライダーだけ動かして処理済みと表示することは厳禁。
- 第一候補の自前PCM処理とAndroid AudioEffectを比較検証し、機器間で一貫した10バンド挙動を提供できる方式を採用。
8-3. DSPチェーンの設計原則
- 各処理は単独で有効化/無効化可能。ただしDirectを選んだ場合は全部バイパス。
- Gain、EQ、Width、Limiterの適用順は測定した結果で選ぶ。必要な場合はLimiter前段に安全なヘッドルームを確保。
- 音声エフェクトの`release()`漏れ、セッションID変更への追従漏れ、アプリ外の音声ストリームへの誤適用を禁止。
- バックグラウンド/画面回転/HyperIsland操作中も同じDSP設定を保持。
- 再生速度変更、ギャップレス、クロスフェードを追加する場合、DSPのリセットや境界処理でクリックノイズが出ないこと。
9. 10バンドEQとプリセット（必須）
9-1. UIと信号仕様
- 周波数中心値の初期目安：`31 / 62 / 125 / 250 / 500 Hz / 1 / 2 / 4 / 8 / 16 kHz`。
- それぞれ`-12 dB〜+12 dB`を基本とするが、実装方式・ナイキスト周波数・機器能力によって適切な有効範囲を設定。+12 dBをそのまま常用推奨しない。
- 初期値は全帯域0 dB。0 dB位置が分かり、ダブルタップまたは「リセット」で0に戻せる。
- 手動の「プリアンプ／全体ゲイン」を用意。ただし歪みを避ける自動ヘッドルームが優先される設定ではその理由を明示。
- 周波数カーブのプレビューを表示（必要に応じCanvas描画）。カーブは実際に使用するフィルター特性から算出し、架空のスペクトラム表示にしない。
- 日本語ラベルと小さな値表示、適切なスライダーのタッチ領域、視覚と音響の両方を確保。
- Liquid GlassはEQの画面全体に貼らない。切替ボタン・プリセット選択・モードスイッチなどにのみ適用。スライダーの読みやすさが最優先。
9-2. プリセット
フラット / バランス / 低音強調 / ボーカル / 明瞭感 / ソフト / カスタム
- 各プリセットの周波数値とGainをコードまたはデータに定義。単なるプリセット名を並べるだけでは不可。
- 各プリセットは控えめな初期値を使用し、過剰な低音ブーストや高音強調を避ける。
- カスタムはユーザーが独自名称で複数保存・変更・削除できる。
- フラットはバイパスまたは0 dB。自動補正や音量均一化が別途ONの場合は「EQフラット」と「全DSP OFF」を区別する。
- アルバム/ジャンル/曲ごとのEQ自動上書きは初版では行わず、意図しない音色変更を防ぐ。
9-3. DSP数値安全性
- 複数バンドを同時ブーストすると加算でデジタルクリッピングが起きる。EQ前段のゲイン低下、ピーク計算、必要時Limiterを組み合わせる。
- +6 dBのプリセットを設けた場合は十分なヘッドルームが確保できたか実測する。
- フィルター係数変更は一定時間で補間、または旧新フィルター出力を短いクロスフェードで切り替え、ジッパーノイズ・ポップ音を防ぐ。
- float処理のNaN/Infinity対策、PCMへの量子化・飽和処理、ステレオ左右同一条件でのテストを実装。
- 16 kHz帯域はサンプルレートが低いと有効範囲が狭くなる。Nyquist以下で適切に設計し、対応不能なら安全に制限。
10. LUMA Auto：自動音質最適化（必須・非AIの実働版）
10-1. 名称と根拠
ユーザー向け名称は`LUMA Auto`（自動音質調整）。AIモデルが存在しない段階で「AIが失われた音を復元」「AIによる高音質化」と表示しない。

自動補正では、曲の特性に応じて小さなEQ補正を提案/適用する。元音源の音色を保つため、極端な変化を避ける。
10-2. 解析と適用
1. 楽曲メタデータに付随する信頼できる情報があれば利用するが、ジャンル名だけで補正を決めない。
2. 解析対象の一部サンプル、または全曲の軽量バッチ解析（必要時）から、帯域別エネルギー、スペクトル重心、過度な低音/高音の偏り等を推定する。
3. 楽曲の平均特性から`AutoToneProfile`を生成。最大補正量は初期値±2 dB程度を上限とし、保守的に補正。
4. ボーカルの存在やジャンルを高確度で識別できると断定しない。推定の曖昧さをUIで誇張しない。
5. 計算済みのプロファイルをRoomにファイル識別子・更新情報・解析バージョンと共にキャッシュ。変更なしで再解析しない。
6. 曲が切り替わる際はEQ係数を短く滑らかに遷移し、急な音色変化を回避。
7. Autoと手動EQは加算しすぎない設計にする。`手動EQを優先／Autoを軽く加算`のルールを固定し、合成した最終周波数特性を表示可能にする。
10-3. スキャン高速化との両立
- Auto解析をStage A/Bの完了条件に絶対に入れない。 v3のStage Cよりもさらに低い優先順位の専用ジョブとして実行。
- デフォルトではユーザーがAutoをONにするまでは既存曲の全件解析を開始しない。
- 解析中も曲は普通に再生できる。プロファイル未完成の曲は手動EQ/フラットで先に再生。
- 再生・高負荷なフォルダースキャン・バッテリー節約時には解析の並列数を絞るか延期する。
- フォルダーを解除した場合、元のファイルを触らず解析キャッシュのみ削除/無効化する。
11. Loudness Normalize：音量均一化（必須）
11-1. 目的と意味
楽曲ごとのラウドネス差を抑え、曲変更のたびに音量調整しなくて済むようにする。波形ピークを全部同じ大きさに揃えることとは違う。
- EBU R128のラウドネス測定の考え方（ITU-R BS.1770に基づくLUFS/K-weighting/ゲーティング）を参照する。
- EBU R128の放送用基準値 -23 LUFSを、そのまま音楽プレイヤーの標準出力に強制しない。 例としてユーザーの選択目標`-16 LUFS`を初期案とし、`-18 / -16 / -14 LUFS`等を設定で選べる。数値は実機と音源で確認して調整。
- アルバム単位（アルバム内の音量差を保つ）と`曲単位`（トラック間を揃える）を選択可能にする。
11-2. メタデータ優先・解析は後段
1. ReplayGainやR128対応メタデータ（例：トラック/アルバムのゲイン、必要に応じてピーク情報）を先に参照。タグの単位、参照ラウドネス、変換仕様、規格差を調査し、ゲイン値を無条件にLUFS値として扱わない。
2. タグが不足した曲のみ、必要時にオフラインでLUFS値を解析。
3. 結果はRoomにキャッシュ。ファイル変更がない限り再解析しない。
4. 解析結果がない曲は強引に音量を推測せず、`解析待ち`等として安全に再生。
5. ファイルのデータや埋め込みタグを自動書き換えしない。
11-3. クリッピング対策
- 目標音量への増幅は上限を設定（初期例 +6 dB まで）。大きすぎる補正を避ける。
- ソースのピーク/True Peak情報を使い、必要なときはゲインを下げる。True-Peak検出/リミッターを実装していないのに`-1 dBTP保証`などと表示しない。
- EQのゲインとLoudness Normalizeのゲインが累積するので、合成ゲインのヘッドルームを管理する。
- 曲ごとに急な音量差が生じないよう、曲切替時の適用ゲインの遷移/ランプを設計する。
- Volume Normalizeは本来のダイナミクスを保持するゲイン補正が基本。勝手に全曲へ強いコンプレッションを掛けない。
12. ステレオ幅・その他DSP（段階実装）
12-1. Stereo Width（必須）
- ステレオ幅を`0〜120%`程度の範囲で設定。初期値100%。モノラル音源では無効/説明表示。
- Mid/Side例：`M=(L+R)/2`, S=(L-R)/2、`L'=M + width*S`, R'=M - width*S。この式は設計概念。実装ではレベル・ピーク・位相を確認。
- 極端な拡張は中央定位を壊し、位相差やモノラル互換性の問題を起こす。初期設定はOFFまたは100%とし、`100%超は音色や定位が変化します`と明示。
- モノラル和信号での低域減衰、左右レベル差、クリッピングを検証し、必要なら帯域別適用を制限。
12-2. Limiter / Dynamics（実装品質を優先）
- ヘッドルームを適切に確保するための安全なリミッターは採用可能。ただし、波形を常時押しつぶす過度なコンプレッションは禁止。
- リミッターが実際に存在するか、サンプルピークしか見ていないか、True Peakまで扱えるかを分けて記録。
- マルチバンドコンプレッサーや「アナログ温かみ」加工は拡張機能。MVP達成を遅らせない。
- 不要なBassBoost、Reverb、Virtualizerを全部ONにする実装は禁止。「音質改善」という名目だけで音を過加工しない。
13. 音質設定の画面・Liquid Glass統合
13-1. 導線
- Now Playingに小さな`音質`/`スライダー`アイコンを設け、音質設定シートへ移動可能にする。
- 設定画面には サウンド を新設。スタンバイモードでも、画面の主操作を圧迫しない場所から同じ音質状態にアクセスできる。
- 音質パネルはv3で構築したBackdropの共通ガラスコンポーネントを使用。別系統の擬似ガラスを作らない。
- ミニプレイヤー、ライブラリ、Now Playingの既存リデザインは一切後退させない。
13-2. 画面構造
サウンド
  ├─ モード              [ LUMA Enhance | LUMA Direct ]
  ├─ 出力先               EarPods (USB Audio) / Bluetooth / スピーカー
  ├─ EQ                   ON/OFF + プリセット + 10バンド編集
  ├─ LUMA Auto            ON/OFF + 現在曲の解析状況
  ├─ 音量均一化           ON/OFF + 曲単位/アルバム単位 + 目標値
  ├─ ステレオ幅           ON/OFF + 幅スライダー
  ├─ 音質の状態           適用中の処理/未対応機能/出力情報
  └─ 実験的な機能         非AIの試作を「AI補完」と偽らない
- Direct中はDSPの操作を無効表示にするか、Enhanceに切替が必要と説明。DirectなのにEQのスライダーだけ動く状態にしない。
- スイッチやつまみはタップ・ドラッグが正しく動作し、TalkBackラベルと48dp程度のタップ領域を維持。
- 状態表示は`有効（適用中）/ 有効（解析待ち）/ 利用不可 / OFF`を区別。モードの選択だけで「処理成功」扱いにしない。
- 無料・オフライン・アカウント不要を維持。音声ファイルを勝手に外部サーバーへ送らない。
13-3. データ保存
- DataStoreにモード・設定値・プリセットの選択を保存。
- RoomにカスタムEQプリセット、曲別LUFS/Auto解析結果、解析バージョン、更新キーを保存。
- Room migrationは非破壊的に実装し、元のライブラリ・プレイリスト・URI権限・再生位置を保持。
- デバイス別プリセットは任意の拡張。最初からEarPods専用と誤認させる特性補正や根拠のないターゲットカーブは付けない。
14. LUMA DirectとUSB-C EarPodsの両立
14-1. 優先実機構成
- 主要端末: Xiaomi 14T
- USB接続イヤホン: Apple EarPods USB-C版
- Bluetooth（既存のイヤホン）や内蔵スピーカーでの標準再生も維持する。
14-2. モード切り替え要件
- EarPodsが接続された状態でEnhanceを利用できる場合、EQ処理済みPCMをAndroid標準USB音声経路へ出力する。
- Direct選択時はEQ、Auto、Normalize、Width、Limiter等のアプリ独自DSPを確実に無効化。`LUMA Direct = ビットパーフェクト保証`とはしない。
- Android 14+ の`AudioManager.getSupportedMixerAttributes()` / setPreferredMixerAttributes()等で利用できるミキサー属性を検証。ただしAndroid側の経路やMedia3オフロード等の制約により、APIが存在することだけでbit-perfectを断定しない。
- USBの出力サンプルレートが取得できなければ「不明」。ソースの44.1/48kHzをそのままUSB出力周波数と表示することは禁止。
- システムEQや他アプリ効果・オーディオHALの内部処理をLUMAから制御できない場合、その制約を明記。
- 音量を0から最大に跳ね上げる切替は禁止。出力デバイス変更時は状態を更新し、必要なら安全な一時停止を挟む。
- EarPodsの物理ボタンの操作はAndroidが発行するキーイベント/MediaSession経由で受けられる範囲をサポート。全ボタン動作を無検証で保証しない。
- USB接続解除時に内蔵スピーカーへ大音量で突然移行しないよう、デバイス切断に対する再生停止/一時停止をテスト。
14-3. 音声表示の正確さ
表示例：
出力先: USB Audio（EarPods）
ソース: AAC / 44.1 kHz（確認可能な値のみ）
再生モード: LUMA Enhance
適用中: EQ「ボーカル」 + 音量均一化
USB出力フォーマット: OSから取得できなければ不明
ビットパーフェクト: 対象外（DSPによる加工中）
Direct例：
再生モード: LUMA Direct
アプリ内音声補正: OFF
ビットパーフェクト: 未確認（または検証済みの場合のみ「確認済み」）
15. DSEE風の圧縮音源補完・AI処理は別フェーズ
15-1. 可能な範囲と禁止事項
- 音楽の圧縮で失われた高域や微細な成分は、元の正解データなしに完全復元できない。生成的な推定によって聴感が変わる可能性がある。
- 高域シェルフEQやExciterだけを適用し、「AIが復元した」と宣伝しない。
- Sonyの`DSEE`や`ClearAudio+`は商標・独自技術であり、コード・モデル・ロゴ等をコピーせず、あくまで類似の機能コンセプトを研究する。
- まず音質向上の測定基盤と10バンドEQ等を完成させる。AI補完は完成を偽装したトグルボタンを置かない。実験機能が未完成ならUIから隠す。
15-2. 研究を進める場合の実装要件
1. オリジナルの高品質PCMと適法に作成した圧縮版を対にした評価用データを用意。
2. 比較する圧縮形式とビットレート（例：MP3/AAC）を明記。
3. オープンモデルを使う場合、ライセンス、学習/推論条件、性能、配布権利を確認。
4. モデルを使わないExciter等は`高域エンハンサー（実験）`と明記。
5. 推論が可能なら、リアルタイム負荷/レイテンシ/電池消費/聴感差を測り、実機で再生途切れがないことを確認。
6. LUMA Enhanceに実際に接続した時だけ有効化UIを出し、Directでは常に処理を避ける。
7. A/B音量を揃え、ブラインド試聴・アーティファクト/高域ノイズ評価で純粋な効果を確認。
16. v4追加機能のテスト、計測、完了条件
16-1. 自動テスト
- EQ: 全0 dBのほぼ恒等性、単独バンド±3 dBの伝達特性、左右チャンネル保持、44.1/48kHz差、バッファ分割違い、極端設定の歪み防止。
- DSP切替: Enhance→Direct→Enhanceで設定が正しく反映され、Directは完全バイパスされる。
- Gain: 入力波形のピーク・クリッピング、NaN/Inf、Limiter経路の安全性、無音入力への挙動。
- Loudness: 解析済み値のキャッシュ、トラック/アルバム切替、ReplayGain等の単位扱い、目標ゲインと上限の検証。
- Auto: 解析値がない曲、破損曲、サイレント、モノラル音声、部分ファイルでも落ちずに再生。
- Persistence: アプリ再起動・Room migration・フォルダー権限再取得後も設定が消えない。
- MediaSession: 外部操作とモード変更が同一の再生状態を参照する。
16-2. 実機テストの表
ケース	期待動作	記録する指標
44.1kHz MP3 → EarPods	Enhance EQ適用、音切れなし	音声処理状態、CPU、 underrun
48kHz AAC → EarPods	EQ/Autoの安全な動作	ピーク、音量差、再生連続性
FLAC → EarPods	DirectとEnhanceの切替	ルーティング、出力形式の取得可否
Bluetooth接続	通知・物理ボタン・DSP	再生継続、DSP適用可否

USB抜き差し / 画面回転 / スタンバイ	大音量暴発・クラッシュなし	経路変更/復旧ログ

17. 開発の進め方（Codex / 実装エージェントへの作業指示）
Step 1: 既存コードの監査
- 画面構成・Composable・Theme・再生サービス・Scanner・Repository・Room・画像ロード経路を把握。
- 上記スクショと実装を比較し、問題箇所の具体的なファイル名/Composable名を列挙。
- スキャン遅延を処理段階ごとに計測し、最大のボトルネックを特定。
Step 2: 読み込み高速化（先行実装）
- Stage A/B/Cの分離、逐次表示、差分スキャン、キャッシュ、失敗時復旧を実装。
- まず曲一覧がすぐ出て再生できる状態を作る。
- バックグラウンド再生と競合しないことをテスト。
Step 3: Backdropの技術検証とデザインシステム導入
- 現行のKotlin/Compose/AGP・minSdkを確認し、Backdropの固定バージョンとAPIの互換性を解決。デバッグ画面でライブ背景サンプリング・屈折・タッチの試作を実施。
- 成功したら`designsystem/glass/`の共通コンポーネントを実装し、ライブラリにないサンプルUIを誤ってimportしない。
- 既存画面を個別にその場しのぎで直さず、色・余白・フォント・Shape・Surface・アイコン・Glass Materialを共通化。
- ライブラリ、ミニプレイヤー、Now Playingを全面改修。
- スクリーンショットを採り、設計意図と異なる余白・文字・色を再調整。
Step 4: 残りの画面と動作
- アルバム、検索、プレイリスト、歌詞、設定、スタンバイモードにUIルールと適切なBackdrop効果を適用。
- AndroidのInsets、ジェスチャーナビ、画面回転、フォント拡大を確認。
- アニメーションの負荷を測り、端末性能に応じて品質を調整。
Step 5: 音質処理の実装と検証
- 下記7〜16章に従って、実際のPCM処理エンジンを段階的に実装。UIだけの機能追加は禁止。
- 10バンドEQ→クリッピング防止→Loudness/Auto→Stereo拡張の順に実装し、個別ユニットテストとA/B検証を行う。
- Direct切替時にすべての自前処理を無効化し、オフロードとUSB出力の実際の経路を確認する。
- スキャン中でも解析処理で音切れを増やさないことを確認する。
Step 6: 完了判定
- ./gradlew assembleDebug 等の実際のビルド成功（環境がない場合は未実施と明記）。
- 可能なら実機スクリーンショット（ライブラリ／Now Playing／読み込み中／スタンバイ）を添付。
- スキャン改善前後のベンチマークと、ガラス有効/無効の描画性能比較、残る制約・未検証項目を報告。
- 見栄えが悪い既存デザインを残して「微調整しました」で終わらせないこと。

21-2. スクリーンショット比較の方法
比較対象はユーザー提供の初版スクショ2枚。
- ライブラリ: 大見出し、検索、カテゴリ、最初の曲/空状態、下部操作の配置を同じ条件で比較。
- Now Playing: 同じ楽曲を使用し、ジャケットの大きさ、タイトル、シーク、メイン操作、下部操作を比較。
- Glass moving backdrop: スクロール前・スクロール後の2枚（可能なら動画）を撮り、背景サンプリングが実際に変わることを示す。
- Standby: 左ジャケット・右操作とガラス材質を横画面で確認。
- 操作しながらの目視チェックを必須とし、静止画だけをガラスの成功証拠にしない。

21-4. 完了を拒否する条件
次のいずれかを満たす場合、作業完了と報告しない。
- 既存の偽ガラスのalphaや白い枠線を少し調整しただけ。
- Backdrop依存を追加しただけで、実際の背景サンプリングが行われていない。
- ガラスの演出がきれいでも、曲が読めない/再生できない/通知が壊れた。
- 既存ライブラリのRoomデータを破壊的マイグレーションで消した。
- 初回スキャンの進捗バーだけが速く、曲の表示や解析時間は改善していない。
- 毎回全曲タグ/画像を再解析している。
- ガラス有効時にタップ不能、過大なスクロールジャンク、バッテリー負荷が発生しているのに放置した。
- 音質向上のスイッチ・EQスライダーだけ作り、実際のPCMへ何も適用していない。
- PCMのピークが0 dBFSを超えてクリップするのに安全策がない。
- DirectモードでEQ/Auto/Normalizerが動く、または未確認なのに「ビットパーフェクト」と表示する。
- 検証していないのに「Apple Liquid Glass完全再現」「USBビットパーフェクト対応」「HyperIsland確認済み」と書いた。
